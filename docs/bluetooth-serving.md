# 현장 배식 블루투스 연결

PC의 블루투스 설정에서 **HC-05 / HC-06**을 먼저 페어링합니다. 현장 배식 페이지(`/`) 위의 **블루투스 연결**을 누르면 브라우저의 장치·포트 선택 창이 열립니다. 해당 모듈 또는 블루투스 COM 포트를 선택하세요. UUID 입력은 필요 없습니다. 통신 속도는 기본 9600 bps이며 **통신 설정**에서 아두이노·모듈 설정에 맞게 변경할 수 있습니다. 기존 학생 확인, 알레르기 차단, 선주문 및 좌석 배정은 유지합니다.

## 장치와 주고받는 데이터

기본 전송은 UTF-8 숫자와 LF(`\n`)입니다. 밥 2회, 반찬 1회, 국 3회를 선택하면 다음 **세 번의 쓰기 작업을 순서대로 완료**합니다. 내부 Firebase 배열은 밥·국·김치 순서이므로 전송할 때 밥·반찬·국으로 변환합니다. 0회도 생략하지 않습니다.

```text
2\n
1\n
3\n
```

장치에서 이름이 필요한 경우 ‘이름 포함’ 형식을 선택합니다.

```text
밥:2\n
반찬:1\n
국:3\n
```

장치 응답도 UTF-8로 전송합니다. 권장 형식은 각 문구 뒤에 LF를 붙이는 것입니다.

```text
배식 시작\n
배식 완료\n
```

세 전송이 끝나면 시작 응답을 기다립니다. `배식 시작` 이후 진행 중 화면을 표시하고, 그 다음 `배식 완료`를 받으면 완료 기록을 저장하고 마지막 화면으로 이동합니다. 시작보다 먼저 온 완료 응답, 중복 응답 및 관련 없는 문자열은 완료 처리하지 않습니다. 응답이 여러 알림이나 UTF-8 바이트 경계로 나뉘어 도착하는 경우도 처리합니다. 타이머로 배식을 완료 처리하지 않습니다.

## 연결 및 오류 처리

- HC-05 / HC-06의 Bluetooth Classic SPP 연결을 Web Serial로 사용합니다. 별도의 UUID 입력이나 BLE GATT 설정은 없습니다. 모듈은 PC와 먼저 페어링되어 있어야 합니다. Windows에서 COM 포트가 여러 개면 해당 모듈의 송신용 포트를 선택합니다.
- PC용 Chrome 또는 Edge의 HTTPS 환경(개발 시 localhost)에서 사용합니다. 사용자가 연결 버튼을 눌러 포트를 선택해야 합니다. 연결 후 같은 포트의 입력 스트림에서 장치 응답을 계속 읽습니다. USB 시리얼 포트도 선택 창에 함께 나타날 수 있습니다.
- 통신 속도는 웹, 아두이노 코드, 모듈 설정을 서로 맞춥니다. 9600 bps는 기본값이며 실제 모듈 설정을 보장하는 값은 아닙니다. UART 설정은 8 data bits, no parity, 1 stop bit, no flow control입니다.
- 전송을 시작한 뒤에는 배식량 수정, 새로운 학생으로 초기화, 연결 설정 변경을 막습니다. 식사 중 좌석을 반납하는 기존 동작은 변경하지 않습니다.
- 연결 끊김이나 일부 전송 실패 후 자동 재전송하지 않습니다. 화면을 새로고침해도 미확인 작업을 이 브라우저에 남겨 중복 전송을 차단합니다. 장치 동작을 멈추고 실제 배식 여부를 확인한 뒤 **장치 확인 후 작업 종료**를 누릅니다. 미완료 선주문은 관리자 확인 전 `processing` 상태로 유지합니다.
- 실제 배식 완료 후 Firebase 저장만 실패한 경우 **완료 기록 저장 재시도**로 저장만 재시도하며 장치에 다시 보내지 않습니다. 동일 작업의 대기 인원 감소는 한 번만 반영합니다.
- 응답에 작업 ID가 없는 간단한 프로토콜이므로 장치의 오래된 응답이 새 작업에 섞이지 않도록 펌웨어에서 작업별 응답을 끝내야 합니다. 확인되지 않은 작업은 자동으로 다음 작업으로 넘기지 않습니다.

## Firebase

기존 배식 기록 경로와 수량 필드는 유지합니다.

- `students/{uid}/serve/{key}/hardware`: `sending`, `waiting`, `serving`, `complete`, `error`, `manual_review` 상태 및 시각
- 선주문 두 경로 `preorders/{date}/{uid}`, `students/{uid}/preorders/{date}`: 전송 준비 시 `processing` / `processingAt`, 장치 완료 확인 후 `fulfilled` / `fulfilledAt`
- `stats`: `queueCount`와 `bluetoothCompleted/{uid}_{serveKey}`를 같은 트랜잭션에서 갱신하여 완료 기록 재시도의 중복 차감을 방지합니다. 기존 Firebase 규칙이 `stats/queueCount`만 허용한다면 이 트랜잭션에 필요한 `stats` 읽기·쓰기 권한을 관리자용 접근 정책에 맞게 조정해야 합니다. 데이터베이스를 공개하는 규칙을 추가하지 않습니다.

## 검증

`node tests/serving-bluetooth.test.mjs`로 순서, 0회, UTF-8 분할, 중복 입력·응답, 연결 실패와 조기 응답을 확인할 수 있습니다. 브라우저 모의 장치 검사에서는 현장 수량 선택→전송→응답별 화면 전환, 타이머 자동 완료 제거, 선주문 상태, Firebase 저장 재시도, 일부 전송 실패 및 새로고침 후 중복 차단도 확인했습니다. 실제 장치와의 무선 연결은 별도 확인이 필요합니다.

연결 방식 참고: [Chrome Web Serial](https://developer.chrome.com/docs/capabilities/serial), [Bluetooth Classic SPP 포트 선택](https://developer.chrome.com/blog/serial-over-bluetooth/).
