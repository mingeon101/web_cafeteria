# Serial1 char 펌웨어 연결

제공된 Mega 스케치는 `Serial1.begin(9600)` / `Serial1.read()`로 ASCII 숫자 문자 3개를 읽습니다. HC-05/HC-06을 PC와 페어링한 뒤 웹에서 블루투스 포트를 선택합니다. 모듈 TX → 메가 RX1 19번, 모듈 RX → 메가 TX1 18번으로 연결합니다.

현장 전송은 밥 → 300ms 대기 → 반찬 → 300ms 대기 → 국 순서이며, 매번 문자 **1바이트**만 씁니다. 예: 밥 2회·반찬 1회·국 3회는 `[0x32]`, `[0x31]`, `[0x33]`으로 세 번 따로 전송합니다. 줄바꿈, 이름, JSON, 이진 정수 바이트를 추가하지 않습니다. 0회는 ASCII `0`(0x30)으로 반드시 전송합니다.

수량은 0~9 정수만 가능합니다. 10 이상을 잘라서 보내거나 두 글자로 보내지 않습니다. 현장 제출 전에 검증하여 배식 기록 생성·선주문 상태 변경·장치 쓰기 없이 차단합니다. 기존 선주문의 10 이상 수량은 수정해야 합니다. 이전 parseInt 구분자나 타임아웃에 의존하지 않습니다.

세 쓰기가 끝나면 시작 응답 대기 없이 진행 중으로 표시합니다. `배식을 시작합니다`는 선택적 진단 출력으로 받고, `배식을 완료했습니다`를 받으면 Firebase 완료 저장 후 마지막 화면으로 이동합니다. 기존 응답 호환, 콘솔 로그, 오류·끊김 후 자동 재전송 금지, 중복 방지와 저장 재시도는 유지합니다. 급식시간·학생 확인·알레르기·좌석 로직은 변경하지 않습니다.

기존 `students/{uid}/serve/{key}/hardware` 경로에 장치 상태를 기록하고, 선주문은 processing → 완료 응답 후 fulfilled로 갱신합니다. `stats` 트랜잭션은 queueCount와 주문별 bluetoothCompleted 마커를 함께 갱신합니다. 관리자용 Firebase 규칙에서 필요한 읽기·쓰기를 허용해야 하며 이 변경에서 규칙을 수정하지 않습니다.

## 숫자 테스트 페이지

`/bluetooth-test/`에서 1·2·3번 입력칸에 각각 0~9 한 글자를 넣고 해당 버튼을 누릅니다. 누른 값만 1바이트로 전송합니다. 스케치에 세 값을 전달할 때는 1→2→3 순서로 누르세요. 스케치는 번호를 받는 것이 아니라 도착한 순서대로 그룹 1·2·3에 할당합니다. Firebase 저장이나 다른 값 자동 전송은 없습니다. 로그에서 문자, hex, byteLength를 확인할 수 있습니다.

## 검증

`node tests/serving-bluetooth.test.mjs`: 문자 순서·1바이트·0회·연속 두 배치·10 이상 차단·300ms 간격·완료 응답·중복 방지·오류 처리. 모의 Web Serial/Firebase 브라우저 검사로 테스트 페이지의 독립 전송과 현장 완료 흐름, 10 이상 선주문 제출 시 DB 저장 전 차단을 확인합니다. 실물 하드웨어는 연결하지 않았습니다.
